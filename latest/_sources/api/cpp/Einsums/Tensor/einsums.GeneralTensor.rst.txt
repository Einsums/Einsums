      Construct a new Tensor object. Moving ``existingTensor`` data to the new tensor.

      This constructor is useful for reshaping a tensor. It does not modify the underlying
      tensor data. It only creates new mapping arrays for how the data is viewed.

      .. code-block:: text

   .. cpp:function:: void materialize_into(T *ptr)

      Materialize into caller-provided storage instead of allocating.

      The tensor uses ``ptr`` (which must hold at least size() elements and
      outlive every use of this tensor) as its backing storage without taking
      ownership: release() detaches from it and the destructor never frees
      it. Used by the MemoryPlanning arena to place graph-owned intermediates
      at planned offsets in one shared block. Idempotent for the same
      pointer; switching storage requires an intervening release().


   .. cpp:function:: void materialize_into(T *ptr, std::shared_ptr<const void> owner)

      Materialize into caller-provided storage that carries its own keepalive.

      Same contract as the raw overload except for lifetime: holding ``owner``
      is what keeps ``ptr`` alive, so the "must outlive every use" promise is
      kept by construction rather than by the caller. A MemoryPool carve
      arrives this way, and dropping the token - through release(), resize(),
      or the tensor's death, on any thread - returns the bytes to the pool.

   .. cpp:function:: void release()

      Release the backing data storage, returning to deferred state.

      Frees owned memory immediately; external storage (materialize_into) is
      detached, never freed. The tensor retains its dimensions and strides
      but data() returns a sentinel pointer. Call materialize() or
      materialize_into() to re-attach storage.
      Used by FreeInsertion pass to release intermediates after their last consumer.


   .. cpp:function:: void resync_storage() noexcept

      Re-seat this wrapper's cached data pointer on the storage block's current buffer.

      ``detail::TensorImpl`` caches the address it reads and writes through, and a wrapper
      that SHARES a storage block (``shallow_alias()``, and the stand-in graph capture adopts)
      holds its own copy of that cache. Every relocation - ``release``, ``materialize``,
      ``materialize_into``, a resize - republishes the live address as
      ``detail::StorageBase::base`` and counts itself in
      ``detail::StorageBase::generation``, but only on the wrapper that made the call. The
      others keep pointing at whatever the block held when they were built, which after a
      release is memory the block has already freed.

      Calling this before reading through a shared wrapper is what closes that: it costs one
      comparison when nothing has moved, and it is how the generation counter is meant to be
      consumed. Dims and strides are untouched; a relocation moves the buffer, not the shape.

      A block nobody has relocated is still at generation zero, so a wrapper built over
      storage it does not own is left exactly as its constructor set it.

   .. cpp:function:: GeneralTensor<T, rank, Alloc> shallow_alias() const

      A second wrapper over the same storage.

      Same element type, rank, dims and strides as this tensor, sharing the
      buffer rather than copying it: writes through either are visible to
      both. Copy construction deliberately does not do this, so sharing is
      always something the caller asked for by name.

      Graph capture uses it to hold an operand by value without deep-copying,
      which is what lets a captured tensor go out of scope before
      ``execute()``.
