===========================================
einsums::compute_graph::ApproximationRecord
===========================================

.. note::
   Generated from the C++ headers by ``apiary --emit-cpp-docs-json``.

Defined in header ``Einsums/ComputeGraph/Approximation.hpp``.

.. cpp:namespace:: einsums::compute_graph

.. cpp:class:: ApproximationRecord

   One lossy rewrite that has been applied to a graph, and what it cost in accuracy.

   Accumulated on the ``Graph`` and SAVED with its structure, because it is a statement about
   what the graph now computes rather than about how it runs: a caller reading a result off a
   loaded graph is entitled to know that the energy is DF at 1e-5, and no machine can recover
   that from the node list.

   It is three things at once. Provenance for the user, the input to the composition rule that
   lets a second lossy pass decide whether it may apply, and the trigger that widens a
   differential test's tolerance from exact to whatever the records say.

   .. seealso::

      Graph::note_approximation

   .. seealso::

      Graph::approximation_tolerance

   .. versionadded:: 2.0.0


   .. cpp:member:: std::string pass_name

      The pass that applied the rewrite, by ``OptimizerPass::name``.

      Not spelled ``pass``, which is what it wants to be called and is a Python keyword:
      the field would bind to a name no Python source can write down. The saved key matches
      this spelling rather than the shorter one, so the file and the type do not need a
      translation nobody would remember was there.


   .. cpp:member:: double tolerance

      The knob the pass was ASKED for, e.g. a ``thc_epsilon`` of 1e-5. Recorded beside
      ``bound`` rather than instead of it: a pass may well meet its target with room to
      spare, and a composition rule that read the target would spend accuracy nobody used.


   .. cpp:member:: ApproximationEffect effect

      What ``bound`` is a bound on.


   .. cpp:member:: double bound

      The effect the pass STATES it had, in ``effect``'s units. This is what composes and
      what a tolerance-aware comparison widens by.


   .. cpp:member:: ApproximationOrigin origin

      Whether ``bound`` was computed or claimed. Defaults to ``ApproximationOrigin::Asserted``,
      which is also how a file written before this field existed is read: a number cannot be
      promoted to evidence by a newer build reading it.


   .. cpp:member:: std::vector<std::string> outputs

      Manifest names the bound applies to. EMPTY means every output, which is the honest
      answer for a pass that rewrote something feeding all of them.


   .. cpp:member:: std::vector<std::string> spaces

      Index-space names the rewrite involved, by NAME for the reason every other saved
      annotation holds names: an id means nothing in another process.


   .. cpp:member:: std::string setup

      Label of the setup node the rewrite created, or empty when it created none. A
      factorization emits its fitting into one, and the record is where the two are tied
      together for anyone asking what produced these factors.


   .. cpp:member:: std::string measurement

      The TENSOR whose value after a replay is this rewrite's MEASURED error, by name, or
      empty when the rewrite measures nothing.

      A record is written once, at optimize time, so ``bound`` is what the structure claims
      and cannot be what a particular bind found. What a bind can leave behind is a value in
      the graph, and this is where the record says which one, so a caller holding a record does
      not have to know how the pass spells its diagnostics.

      A tensor rather than a parameter, and that is a correction rather than a preference: the
      ``ParamTable`` is integer-valued, so a residual below one truncates to zero there and a
      number that cannot represent what it measures is not a measurement. The precedent that
      works is the error tensor a Laplace quadrature already writes.

      It is also the whole of the rule for a rewrite INSIDE A LOOP. A fit re-fitted at every
      amplitude update writes this tensor once per iteration, so what stands in it when the
      solver stops is the fit's error at the LAST iteration, which is the iteration the
      converged answer came out of. There is no per-iteration history and there should not be:
      the intermediate fits are error in a quantity nobody kept.
